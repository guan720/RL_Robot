## 0. 先回答 ROADMAP 点名要写清的 5 个问题

| 问题 | 手写 Reach（`envs/reach_env.py`） | robosuite `Lift` + `Panda` |
| --- | --- | --- |
| **obs 是什么** | 6 维向量：`[末端xyz(3), 目标xyz(3)]`，都除以 `half_space=0.15` 归一化到 [-1,1] | `OrderedDict`，15 个键：关节角/末端位姿/物体位姿/相对位置 + 拼好的 `robot0_proprio-state`(50) 和 `object-state`(10)，开相机再加 `frontview_image`(256,256,3) |
| **action 是什么** | 3 维**末端位移增量**，[-1,1]，实际位移 = `action × 0.05` 米 | 7 维（`OSC_POSE` 控制器）：`[0:3]` 末端 xyz 增量、`[3:6]` 姿态增量（axis-angle）、`[6]` 夹爪（-1 开 / +1 合） |
| **坐标系 / 单位** | 环境自己的局部坐标，单位米 | **世界系**，单位米；姿态是四元数(obs) / axis-angle(action) |
| **reward 谁给** | 环境代码：`-距离`，进入 3cm 成功圈额外 `+10` | 环境代码：`Lift` 只有物体离开桌面才算 +1（`reward_shaping=False` 时中间过程全是 0） |
| **终止条件** | `terminated` = 进入成功圈；`truncated` = 超过 `max_steps=100` | robosuite 返回 **4 元组**，只有一个 `done`（成功或到 `horizon=1000`） |
| **训练前后哪份参数变了** | 只有 `runs/<run>/model_final.zip` 里的 SAC 网络权重（actor + 2×critic + 熵系数）。环境、奖励函数、评测 seed 全都没动 | 同左 |

**最该记住的一条**：`action` 是**增量**还是**绝对位姿**，决定了整个系统的难度量级。
团队在 `../Agibot_path_IK` 上已经吃过这个亏——绝对 TCP 位姿直搬到 G2 是 0/8 全失败。
以后接任何新机器人，第一件事就是把 action 语义问清楚，别靠猜。

## 2. 实验二（阶段 1a）：随机策略 + 录视频

```bash
MUJOCO_GL=egl python scripts/smoke_random_policy.py --task Lift --episodes 1
# 产出：runs/smoke/<时间戳>/Lift_random.mp4 + result.json
```

本次结果：**1000 步、reward 0.000、success=False、视频 1000 帧 256×256（平均像素 148，非黑屏）**。

### 这个实验不是用来出成绩的

随机策略成功率 0% 是**预期结果**。它的价值是把接口摊开给你看：

- obs 字典逐项打印 → 你知道策略网络的输入到底有什么；
- `action_dim=7`、范围 [-1,1] → 你知道输出该是什么形状；
- `horizon=1000`、`control_freq=20` → 你知道一局是 50 秒仿真时间；
- mp4 → 你**看见**了「随机动作的机械臂在抽搐」长什么样。

最后一条比前面都重要。以后看到策略行为异常，你脑子里要有一个「随机基线的样子」作参照，
否则分不清是策略学坏了，还是接口/坐标系本来就接错了。

### 为什么 `Lift` 随机策略必然 0%

它要求**时序全对**：末端移到方块正上方 → 下降到合适高度 → 姿态对准 → 夹爪闭合 → 抬升。
每一步的概率都不低，但连乘起来在 1000 步内几乎不可能撞上。
这也是为什么抓取任务要么用示范（模仿学习），要么用**密集奖励**（reward shaping）或课程，
纯稀疏奖励 + 随机探索是学不动的。这一点在阶段 2 设计奖励时必须记住。

### robosuite 1.5.2 的 API 差异（照抄网上教程必炸）

| 教程里写的 | 1.5.2 实际 | 脚本里的处理 |
| --- | --- | --- |
| `env.action_space.low/high` | 没有这个属性 | `env.action_spec` → `(low, high)` |
| `obs, info = env.reset()` | 只返回 `obs` | `unpack_reset()` 兼容两种 |
| `obs,r,term,trunc,info = env.step(a)` | 返回 **4 元组** | `unpack_step()` 兼容 4/5 |
| `env.render(offscreen=True, camera_name=...)` | `render()` 不收任何参数，只开窗口 | 取帧走 `obs["frontview_image"]`，退路 `env.sim.render(...)` |

## 3. 实验三（阶段 1b）：第一个真正的 RL 训练

```bash
python scripts/train_reach.py --steps 5000                          # 冒烟，几分钟
python scripts/train_reach.py --config configs/reach_sac.yaml        # 全量 50000 步，本机实测 54.6 分钟
python scripts/show_curve.py --latest                                # 看曲线
```

### 为什么输出是「三行对比表」而不是「一条曲线」

这是本阶段最重要的一条方法论。

曲线只能说明**训练过程中**奖励在涨，它无法排除两种情况：
1. 探索运气好，撞上了几次成功；
2. 评测用的初始状态正好和训练时高度重叠（背题）。

所以 `train_reach.py` 固定同一个评测 seed（12345）、同一批 50 个初始状态，跑三次：

| | 是什么 | 回答什么问题 |
| --- | --- | --- |
| 随机策略 | 没有网络，每步随机采样动作 | 不学习能得多少分（**基线**） |
| 未训练的网络 | 有 SAC 的网络结构，权重是随机初始化的 | 是不是「加了个网络」本身就带来提升 |
| 训练后的网络 | 同一份权重，被 5 万步交互数据改写过 | **参数学习**到底带来了什么 |

只有第三行明显好于前两行，才能说「机器人通过数据学会了任务」。
这就是把「执行了一次任务」和「学会了任务」区分开的唯一干净办法。

### 冒烟结果（5000 步，不够学会，但信号已经出现）

| 策略 | 成功率 | 平均奖励 | 平均步数 | 平均末距(m) |
| --- | --- | --- | --- | --- |
| 随机策略 | 16.0% | -17.976 | 91.6 | 0.2115 |
| 未训练的网络 | 6.0% | -24.090 | 95.2 | 0.2768 |
| 训练后（5000 步） | 18.0% | -7.788 | 83.5 | **0.1063** |

**该看哪一列**：成功率只从 16% 到 18%，几乎没动；但**平均末距从 0.21m 掉到 0.106m**，
成功圈半径只有 0.03m。这说明策略已经在**稳定地靠近目标**，只是还差最后一截精度。

这就是为什么不能只盯成功率：**成功率是阶跃的，距离是连续的**。
学习早期距离先降、成功率后涨；只看成功率会以为「没学到东西」而误判。

### 这张表最该看的三件事

**1. 学习是「相变」，不是「渐变」。**
0→10000 步之间，确定性评测的平均奖励一直是负的（-8.8、-10.2），
看起来毫无进展；**10000→15000 步之间直接跳到 +9.1**，之后就是平台期。

原因：SAC 前期在**探索**，策略是高熵的随机采样；`EvalCallback` 用
`deterministic=True`（取分布均值）评测，而一个还没成形的高熵分布，它的均值动作往往很差。
等到 critic 学到了 Q 值、熵系数降下来，均值动作才突然变得可用。

**对你的实际意义**：训练中途看到评测是负的**不要急着停**。
判断该不该继续，看 `ent_coef` 和 `ep_rew_mean`（训练时的随机策略奖励）的趋势，
不要只看确定性评测。这次 5000 步冒烟时确定性评测 -8.0，但 15000 步就满了。

**2. 平均步数 91.6 → 2.6，比成功率更说明问题。**
成功率 100% 只说明「到了」；平均 2.6 步说明「**几乎直线冲过去**」。
一步最大位移是 `0.05 × √3 ≈ 8.7cm`，目标平均距离 0.19m，2.2 步就是理论下限。
也就是说策略已经接近最优，不是勉强蹭到成功圈。

**3. 变的只有 `model_final.zip` 里的权重。**
环境代码、奖励函数、`half_space`、评测 seed 全都没动。
这就是「机器人通过数据学会了任务」的最小可验证形式——
以后接了真机、接了 LLM，判断「到底学到了什么」用的还是同一套逻辑。

## 4. 指标陷阱：随机基线居然有 16–19%

这是本次实测最值得记下来的一条。默认配置下**随机策略的成功率不是 0，而是约 19%**
（200 局测的）。原因很简单：

- 工作空间只有 `[-15cm, 15cm]³`；
- 每步能走 `5cm`，一局有 `100` 步；
- 随机游走的位移标准差 ≈ `0.05/√3 × √100 ≈ 2.9cm`/维，100 步下来末端几乎均匀地扫过整个盒子；
- 成功圈半径 `3cm` 相对这个盒子不算小。

所以随机撞进成功圈的概率并不低。**如果不查基线就开始训练，你会把「基线本来就高」误读成「学得快」。**

实测四种评测条件下的随机基线：

| 评测条件 | 随机策略成功率 | 平均步数 | 平均末距(m) |
| --- | --- | --- | --- |
| 默认（100 步 / 3cm） | 19.0% | 90.3 | 0.1911 |
| 更短（50 步 / 3cm） | 9.5% | 47.2 | 0.1967 |
| 更严（100 步 / 2cm） | 8.5% | 95.1 | 0.1997 |
| 最严（50 步 / 2cm） | **3.5%** | 49.2 | 0.1930 |

### 三个应对手段

1. **多看几列**：成功率 + 平均步数 + 平均末距。步数下降说明变快了，末距下降说明变准了。
2. **严酷探针**：不改训练，只在评测时收紧条件。
   ```bash
   python scripts/eval_policy.py --ckpt runs/<run>/model_final.zip --episodes 100 \
          --max-steps 50 --goal-radius 0.02
   ```
   基线从 19% 掉到 3.5%，信号就干净了。
3. **固定 seed**：训练前/后、换 seed 复评，都用同一批初始状态，才有可比性。

### 这和 RoboRSI 的指标问题是同一类

之前分析 RoboRSI 时说过：「跨版本累计完成 95/120」和「冻结版本单次成功率 79.2%」回答的是两个不同问题。
这里也是：「默认条件下 18%」和「严酷探针下 2%」回答的也是两个不同问题。

**结论：报成功率必须同时报清楚三件事——评测条件、基线是多少、是不是同一批 seed。**
少任何一件，数字都没有意义。这条纪律从现在就养成，以后写论文/汇报会省掉大量扯皮。

## 5. harness 预览：`scripts/demo_harness_tree.py`

```bash
python scripts/demo_harness_tree.py --tree        # 只看树结构
python scripts/demo_harness_tree.py --ticks 8     # 跑 8 个 tick
python scripts/demo_harness_tree.py --verbose     # 每个 tick 打印完整带状态的树
```

不需要 ROS、不需要仿真器、不需要大模型，纯 Python 几十行，用 py_trees 把「上层框架」跑给你看。

### 树结构

```
{-} harness 主循环
    --> 记录本轮
    [o] 任务调度（谁的条件满足就跑谁）
        {-} 正向 A->B
            --> [A] 有物体?
            {o} 正向 带恢复
                --> 搬运(A->B)
                {-} 恢复后重试
                    --> 恢复动作
                    --> 重试搬运(A->B)
                --> 请求接管
        {-} 反向 B->A
            --> [B] 有物体?
            {o} 反向 带恢复
                --> 搬运(B->A)
                {-} 恢复后重试
                    --> 恢复动作
                    --> 重试搬运(B->A)
                --> 请求接管
        --> 两区皆空(需复位)
```

### 跑出来看到三件事

1. **正反向自动交替**：tick 2 把物体从 A 搬到 B；tick 3 发现 A 空了、B 有物体，自动变成反向 B→A。
   这就是 **reset-free** 的核心——**让两个方向的策略互相替对方复位**，省掉人工摆物体的成本。
2. **三级降级**：tick 1 抓取失败 → 恢复动作也失败 → 请求接管（人类 / LLM）。
   `请求接管` 这个叶子节点就是你研究里「LLM 接管」的插槽，现在只打印一行，
   将来换成「调用大模型生成恢复方案 + 通过受约束的机器人 API 执行」。
3. **失败必须能被看见**：tick 1 的根节点状态是 **FAILURE**。
   这个 FAILURE 是上层框架要记账的信号，决定要不要把这段轨迹送去训练、要不要升级给人。

第 3 点是我在这个 demo 里特意修掉的一个语义 bug：原本兜底分支是个无条件 `Success`，
接管失败后根节点仍然报 SUCCESS —— **失败会在统计里消失**。
换 harness 框架时（py_trees / BehaviorTree.CPP / RoboRSI）都要专门检查这一点。

### 这棵树现在还不管什么

- 搬运技能**内部**怎么做（规划？RL 策略？大模型调用？）→ 技能层，阶段 3
- 失败**原因**是什么（感知错 / 抓取位姿错 / 控制抖）→ 诊断层，RoboRSI 的 Reviewer
- 要不要根据这批轨迹训练新版本、训练完能不能发布 → `registry/`，阶段 3

上层框架管的是**流程**，不是**能力**。能力来自下面的策略层——这也是为什么路线图坚持先做阶段 1。
