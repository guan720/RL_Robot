## 1. 先枚举本轮技术点

1. 共享 θ 是否贯穿正反 actor、Q、target、采样、发布，而非两个独立策略。
2. 弱 base／零成功是否被错误推导为必须抛弃原生动作先验；完整头是否能被对照推翻。
3. queue-MDP 的 X、C、U、reward、next queue、折扣单位是否在同一时间轴。
4. request admitted、result committed、physically activated 是否分开；terminal 例外是否会伪造行为。
5. 提前终局、迟到终局判定、接管、deadline miss、换向和 prime 的边界。
6. C/E/D 的动作梯度、真实执行 mask、BC 质量 mask、TD 资格是否各司其职。
7. 真实 Harness 纠正、影子标签、特权／事后监督、微步反馈是否有独立数据资格。
8. 默认训练平台的 target、概率接口和 buffer 能否直接满足本项目定义。
9. 等预算动态 BC 对照、独立 policy 评估与双向迁移的证据门槛。
10. 通用框架与本体 adapter 的边界，避免用品牌适配决定算法优劣。

## 4. 必要缺陷与可选增强

**必要缺陷：本轮未发现足以要求修改冻结设计的逻辑错误或关键遗漏。** 共享 θ、队列增广 TD、真实请求终局样本、接管隔离和监督分流在三份技术文档间基本一致；研究材料也没有把源码存在冒充默认兼容或本项目实测。

可选增强，不作为本轮 NEEDS_REVISION 的理由：

1. 平台迁移 checklist 可增加“确定性 actor 不需要 log_pi／entropy 温度路径”这一显式条目。当前总契约已要求 loss 适配，但固定 RLinf worker 的具体差别值得在实现 issue 中列出。
2. 将 T06 §5.1 的存活概率重加权限制转成一个两状态共享参数的最小数值消融，直接比较保留／筛除 actor terminal 行；避免后续实现者将“不给该样本 actor 梯度”误读为普遍无偏定理。
3. R01 §8.3 等概览表中的“实际执行且有后继可用于 TD”可补一句“还须满足所选 MDP 时序契约”，让单独阅读专项的人更容易找到 T06。正文已充分限制，故不是现有方案缺陷。
4. 冷启动比较可预先保存一份路线决策表：初始双向能力、关键动作覆盖、合格 TD 密度、独立双向改善、实体/GPU/GPT 总成本。当前要求已存在，表格只是提高后续执行一致性。

## 5. 实测门槛与 PASS 的范围

本轮要求设计给出可检验门槛，**不要求现在已经实测**。冻结输入已明确以下仍待实现或验证：

- 手算队列轨迹通过 request／commit／activation、n 步折扣、提前终局、超时与中途接管边界；检查实际计算图中的 Q／BC mask。
- 原生头、完整头、RT-EXPO 在相同双向示范和纠正预算下比较；每种时间协议先独立验收，不能因表面张量一致而混 replay。
- 在固定设备和推理配置下测自然延迟、选 n，记录 deadline miss、终局样本丢失与接管删失比例；高删失时不能宣称算法已得到充分无偏数据。
- 同一 checkpoint 双向独立评测，同时报告系统辅助能力与人工成本；需能区别 RL 额外收益和动态 BC 所带来的收益。
- 通用 adapter 的回放测试通过后，还需目标本体的实际动作／停止／反馈核验；软件接口通用不等于跨本体权重已经通用。

因此 PASS 的含义是：这份设计已经把主要反例、源码兼容性缺口和可推翻的选型门槛写清楚，可以进入实现与实验；不是确认任何候选已部署成功、零成功冷启动必然可行或自主学习已经成立。
